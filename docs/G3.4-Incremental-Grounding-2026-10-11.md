# G3.4 incremental grounding maintenance

## 日本語

### 優先順位と実装

前回の学習/query交互実行で、低query密度では全index再構築が負担だったため、appendの差分更新を優先した。
一次EventとPrimitiveは維持し、役割対とidentityの同一Event witnessを更新する。通常の追加学習では新しい支持Event
だけを読む。新しいPrimitiveはその支持証拠から作り、既存Primitiveの支持数が想定と違えば対象entryを再作成する。
query時にPrimitive数や参照の置換を検出した場合は、従来通り全再構築へfallbackする。

```python
from risa.engine.primitive_grounding import build_primitive_grounding

build_primitive_grounding(state, incremental=True)
# 以後の通常appendは差分更新する。
result = compose_to_effect(state, start_action, target_effect, use_grounding_index=True)
```

既定の全走査と従来の全再構築modeは変更していない。incrementalを明示選択する。
同じEventの再投入はtrain_eventsで除外され、二重計上しない。既存IDの低レベルingest置換や、以前欠落していた証拠の
到着時にはcacheを無効化する。直接Event/証拠集合を編集する場合は明示invalidateが必要。
無効化・load後に差分modeを続ける場合は再度`build_primitive_grounding(..., incremental=True)`を呼ぶ。
保存schemaと出力内容を変えず、index自体は保存しない。

index内の`payload_bytes`は差分更新後にNoneとし、古い値を返さない。
現在の論理サイズは`grounding_payload_bytes(index)`で明示計測する。
更新にはwitness集合のコピー・並べ直しが残るため、証拠の追加読み出しが1回でもCPU費用が常に一定とは主張しない。

### 比較条件と完全一致

以前のfixtureの3 seed×2世界、1/3/24 Event追加、更新後1/40 queryを維持。
全走査・全再構築・差分更新の3 armをstepと反復ごとに循環させ、3回反復した。
更新の費用は学習時間へ含め、query時間だけを比較しない。

全108軌跡、反復を含む97,416 query比較で完全`CompositionResult`差0。
各更新でシリアライズ内容が一致し、各軌跡の96 Event時点で3 armの実保存バイト列を比較した。
復元後は全40 queryを再照合し、一致した。学習初期にも参照実装と同じ結果であることの確認で、
初期の全予測が環境oracleに正解するという主張ではない。

| 追加Event/更新 | 全再構築の累積Event参照 | 差分更新の累積Event参照 | 差分modeのquery内構築参照 |
| ---: | ---: | ---: | ---: |
| 1 | 4,578 | 96 | 0 |
| 3 | 1,554 | 96 | 0 |
| 24 | 240 | 96 | 0 |

各値は96 Eventまでの1軌跡当たり。全seed/world/query密度/反復で同じ。
1 Eventずつ更新する条件の証拠参照削減は97.9%。従来のwarm参照0だけでなく、維持の読み出しも数えている。
論理indexサイズは独立世界1,325 byte、依存世界1,343 byteで従来と同じ。
この値はPython heapやRSSではない。実保存内容は3 armで同じ。

### 時間と判断

下表は各条件18標本（3 seed×2世界×3反復）の**学習＋query合計時間**の中央値、単位ms。
保存/復元の一致確認は計測区間外。96 Eventの小規模開発測定であり、本番p99・大規模性能の保証ではない。

| 追加Event | query/更新 | 全走査 | 全再構築 | 差分更新 |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 1 | 173.204 | 183.357 | 174.875 |
| 1 | 40 | 439.413 | 329.333 | 313.117 |
| 3 | 1 | 80.781 | 82.178 | 77.865 |
| 3 | 40 | 155.896 | 118.337 | 117.843 |
| 24 | 1 | 31.479 | 33.139 | 32.447 |
| 24 | 40 | 44.365 | 36.888 | 37.747 |

1 Event＋1 queryでは全再構築より合計4.6%短縮したが、全走査より約1.0%遅い。
1 Event＋40 queryでは全走査より28.7%、全再構築より4.9%短縮。
24 Event＋40 queryでは全再構築より2.3%遅かった。この差を隠さず、差分更新を常時有効にしない。
query単独の中央値は全6条件で全再構築より短いが、その一部を学習側の維持費用が相殺する。

## English

Prioritize append maintenance because full grounding rebuilds were costly with sparse queries.
Explicitly build with incremental=True, then query with use_grounding_index=True. Maintain same-Event
role/identity witnesses from added support; preserve raw evidence. Unexpected support/reference changes
rebuild entries or fall back to full construction. Replacement ingestion invalidates the cache; direct source
edits require explicit invalidation. After invalidation/load, select incremental mode again explicitly.
Defaults and persistence schema are unchanged. Query grounding is not automatically enabled.

The unchanged two-world fixture compares scan/full-rebuild/incremental arms with cyclic execution order,
three seeds and three repetitions. All97,416 complete query comparisons, per-update serialized states,
108 final three-arm file comparisons and reloaded panels agree. At one/three/24-Event updates, cumulative
maintenance reads fall4,578/1,554/240→96 per trajectory to96 Events; incremental query build reads are zero.
Logical summary bytes stay1,325/1,343; this is not heap/RSS or evidence compression.

The table above includes training plus query time, with18 samples per configuration. At one Event/one query,
incremental is4.6%faster than full rebuild but1.0%slower than scan. At one Event/40 queries it improves28.7%
over scan and4.9%over rebuild. At24 Events/40 queries it is2.3%slower than rebuild. Keep opt-in and retain
these negative comparisons. Update-time witness copying/sorting remains; a single evidence read does not
prove constant CPU work under role diversity. Tests cover diverse joint roles, equality changes, duplicate
ingestion, replacement, actual split, missing evidence and reload. Next measure diverse-witness maintenance
and additional query densities before automatic selection/default enablement. No candidate/condensation claim.
