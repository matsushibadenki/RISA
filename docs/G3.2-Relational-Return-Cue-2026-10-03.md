# G3.2 Relational Return Cue — Development Control

## English

This control makes A→B→A return identifiable from observed topology rather than
an explicit `regime:A/B` context tag. A target is mounted on a platform; the
platform's `coupled_to` edge points toward an anchor in A and away from it in B.
The relation vocabulary is identical. The target's one-hop signature is the
same, while its two-hop signature differs. Entity identities and binding
variable names vary across observations and held-out queries. No target role,
effect label or precomputed signature is supplied in the raw fixture.

Training retains the three indoor/sheltered/outdoor contexts and reversed B
outcomes from the existing fixture. It uses six A1 Events and twelve Events in
each subsequent phase, five development seeds, and all seven switches. There
are no nuisance tags in this control: this isolates return-cue routing from
unseen-context transfer. Every arm and baseline consumes zero supervised
adoption labels. This does not provide adopted merge or dormancy opportunities;
the mechanism gate still fails, so it is not the final lifecycle ablation.

A/B panels are paired with identical actor, target, context and bindings; only
the second-hop edge direction changes. Removing that edge makes all 24 paired
queries identical with opposite labels per seed (perfect-B immediate-A ceiling
0). Keeping it removes all query conflicts (ceiling 1). Renaming identities and
binding variables preserves the induced role signatures.

The table baselines use RISA's existing deterministic role extractor at one or
two hops, consistently for observations and queries. They receive the same raw
relations and no supervised labels. A preprocessing control also applies this
same two-hop projection at the RISA model boundary, explicitly supplying the
computed role on every observation and query. It isolates evidence routing;
it does not change default role-free inference or establish candidate benefit.

| Model | B exit accuracy | Immediate A return accuracy | B recovery Events | A2 recovery Events |
| --- | ---: | ---: | --- | --- |
| Default RISA, all seven arms | 100% | 0% | 9–12 | 10–12 in four seeds; censored in one |
| One-hop latest table | 100% | 0% | 5–7 | 5–6 |
| One-hop count table | 100% | 0% | 8–10 | 8–11 |
| Two-hop latest/count tables | 100% | 100% | 5–7 | 0 |
| RISA with shared two-hop projection | 100% | 100% | 5–7 | 0 |

All models start with A1 accuracy 1.0. Default RISA ends A2 at 1.0 in every seed,
but seed 71 reaches it too late to satisfy the three-sample recovery criterion.
B adaptation qualifies every seed's retention interpretation, unlike the prior
nuisance control. Touch counts and Replay costs are retained in each RISA
outcome; projection controls also execute the full training and Replay path.
No independent final seeds have been used.

The evidence narrows the problem: default Event role readouts use a one-hop
signature, while query role resolution can expose a two-hop signature. Merely
making the deeper cue available does not place learned outcome evidence under
that signature. The preprocessing control restores immediate return without
new labels or split/merge/dormancy gains, and simple two-hop tables match it.
This is an evidence-routing limitation, not structural-intelligence advantage.

Next: implement an opt-in, consistently scoped two-hop role readout for Events
and queries, with persistence/rebuild equivalence and controls for missing
relations, true same-role drift, and unseen entities. Keep the one-hop reference
and these strong tables. Do not silently switch every ambiguous query to a
deeper role or treat a preserved readout as validated concept formation. A
valid lifecycle world still requires adopted mechanisms and independent
validation evidence.

## Native readout implementation — 2026-10-03

English: The opt-in state setting `target_role_readout_hops=2` now scopes
incremental outcome counts, evidence indexing, grounding, recent outcomes and
supporting paths consistently to the deepest available structural role. Raw
Events retain their original empty supplied-role fields. Supplied roles retain
priority. Candidate discovery and candidate matching keep their existing role
semantics; this change concerns predictive readouts. For a target query in this
mode, identity aggregates cannot bypass the selected role. If grounded role
outcomes exist, only those outcomes enter effect selection; otherwise validated
candidate effects remain eligible. Missing role evidence abstains instead of
falling back to a mismatched shallow role or an unscoped known-entity history.
This stricter identity policy is part of the opt-in mode, not the default mode.

All five native controls reach B accuracy 1.0, immediate A-return accuracy 1.0
and A2 recovery 0 Events. B recovery is 5–7 Events, matching the strong two-hop
tables. At A1/B/A2 boundaries, 720 complete `PredictionResult` objects match
both JSON round-trip reconstruction and the full-scan access reference. Tests
also cover actual same-role drift, a known entity reused in both regimes,
missing/disabled relations, supplied roles, invalid configuration and legacy
state migration. There is no structural advantage over the tables and no
split/merge/dormancy adoption evidence. The opportunity gate remains failed.

Schema v5 persists the readout mode because reconstructing depth-two indexes as
depth one would change semantics. Versions through v4 load with the depth-one
default when the setting is absent. Depth one retains legacy query resolution
and inference behavior; newly saved states use v5. Older runtimes reject v5
rather than silently interpreting the mode incorrectly. Configure the state
before learning; changing its setting in place after ingestion is unsupported.
The indexes remain derived from Events. This is a prediction-path result, not a
planner-quality or 100k end-to-end learning result.

```python
from risa.core.state import RisaState
from risa.engine.runtime import train_events

state = RisaState(target_role_readout_hops=2)
train_events(state, events)
```
