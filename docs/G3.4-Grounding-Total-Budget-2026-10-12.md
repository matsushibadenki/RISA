# G3.4 Aggregate lookup budget / 合計lookup予算 / lookup总预算

## 日本語

`build_primitive_grounding(state, incremental=True, total_lookup_budget_bytes=8192)`で、全Primitiveに付随するlookup辞書コンテナの合計を制限する。既存のPrimitive別`lookup_budget_bytes`も指定でき、両方を満たす残余予算で構築・差分更新する。合計残高`lookup_bytes_used`は追加・置換・fallbackで差分管理し、queryごとの全Primitive再集計は行わない。

初回構築はPrimitive IDとwitness行をソートして割り当てる。入りきらないPrimitiveは完全なwitness行を線形検索し、後続の小さいPrimitiveには残余予算を使える。appendは既存割当を優先し、予算超過時は当該lookupを解放する。新規・再構築Primitiveは解放済み予算を利用できる。既に線形になったPrimitiveは空きが出ただけでは再昇格しない。構築時の割当は辞書・setの順序に依存しないが、append時の優先順は学習呼出し順に依存する。query頻度から最適配置するpolicyではない。

合計予算もlookup本体・actor bucket・target辞書のコンテナのみを対象とし、canonical witness行、文字列、Primitive、元Event、RSS全体を制限しない。判定前の辞書拡張や、再構築中の旧新indexの共存など一時的なピークは上限の対象外。各操作完了時に現在のindexへ保持するコンテナ量の上限である。外部が保持する旧index参照も制御しない。無効化後は同一stateの両予算を継承、load後は明示再指定する。保存schema・既定全走査・役割対とidentityの意味は変更しない。

評価は4 Primitive、各24 Event、各側1/2/4/8役割。全走査・線形index・無制限lookup・合計8KiBの4方式を比較する。1回ずつの全Primitive追加とidentity訂正を挟み、各段階64 query（計192）の費用を測る。別枠で各段階96ケースと復元後96ケースを照合する。queryはlookupに割り当てたPrimitiveへの集中と線形Primitiveへの集中を分け、候補on/off、複数役割、未知target、identity反転を含む。

hash seed 0/1/42ごとに4反復、合計12個の新規processを**逐次**起動し、性能測定を重ねない。各process内では方式順を循環し、4反復で各段階の先行順を均衡化する。process間の完全結果digest・実保存SHA256・各段階の割当を照合する。全processでgo0/go1がlookup、go2/go3が線形、保持コンテナは6,880 bytesで8,192 bytes以内だった。hash seed別時間差には実行時期・OS負荷も含まれるため、hashだけの因果効果とは扱わない。

## English

Add `total_lookup_budget_bytes` to cap lookup dictionary containers across all primitives, optionally combined with the per-primitive limit. Maintain the aggregate counter incrementally. Build in sorted primitive/row order; entries that cannot fit use exact linear witness scans. Appends preserve current allocations and release lookup capacity on overflow; new/rebuilt entries may consume it. Existing linear entries do not automatically promote. Append priority follows learning-call order, not query frequency.

This limits retained containers in the current index at operation boundaries, not canonical evidence, strings, total state, RSS, transient growth, coexisting old/new indexes during rebuild, or external references. Preserve budget settings across invalidation on the same state; explicitly reselect after loading. No persistence schema or default scan change.

Compare four arms over four primitives with24 events each and1/2/4/8 roles per side, append and correction phases, and192 timed queries per trajectory. Independently verify96 query cases per phase and after reload. Compare workloads concentrated on lookup-selected versus linear primitives. Run12 fresh processes serially with hash seeds0/1/42 and four rotated repetitions each. Cross-check complete-result digests, saved SHA256 and allocations. All processes select go0/go1 for lookup and go2/go3 for linear, retaining6,880 bytes under8,192. Seed timing differences also include temporal/system-load effects; allocation is not a workload-optimal policy.

## 简体中文

新增`total_lookup_budget_bytes`限制所有Primitive的lookup字典容器总量，可同时设置每Primitive预算。差分维护总余额，按Primitive ID及witness排序构建；装不下的使用精确线性扫描。追加保留已有分配，超限释放lookup，新建或重建项可使用释放的预算；原线性项不会因有空余而自动升级。追加优先级依赖学习调用顺序，不依赖query频率。

预算限制操作完成时当前index保留的字典容器，不限制原证据、字符串、整个状态、RSS、临时扩容、重建时新旧index共存或外部旧引用。失效后继承预算，加载后显式重选；保存schema及默认扫描不变。

四方式比较4个Primitive，每个24 Event、每侧1/2/4/8角色，包含追加与identity修改，每轨迹192个计时query，另验证每阶段及恢复后的96个完整结果。分别集中查询lookup与线性Primitive。逐次启动12个独立process，hash seed0/1/42各四次轮换。跨process比较结果digest、保存SHA256及分配；全部go0/go1为lookup、go2/go3为线性，保留6,880 bytes低于8,192。seed时间差也包含系统负载及执行时段影响，未证明分配策略最优。
